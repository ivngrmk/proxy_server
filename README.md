# Proxy server

Небольшой HTTP CONNECT прокси на стандартной библиотеке Python.
Он создаёт TCP-туннели, в том числе для HTTPS, и не расшифровывает TLS.
Обычные HTTP-запросы без CONNECT не поддерживаются.

## Структура

```text
src/proxy_server.py                   Код прокси
deploy/systemd/proxy-server.service   Служба systemd
deploy/proxy-server.env.example       Пример настроек
deploy/tunnel.env.example             Пример настроек клиента и туннеля
scripts/install.sh                   Установка и обновление службы
scripts/install-client.sh            Установка команд with-proxy и proxy-tunnel
scripts/uninstall.sh                 Удаление службы
scripts/tunnel.sh                    Запуск, проверка и остановка SSH-туннеля
scripts/with-proxy.sh                Запуск команды через проверенный прокси
scripts/lib/client.sh                Общие настройки клиента и HTTPS-проверка
tests/test_proxy.py                  Проверки соединений
tests/test_with_proxy.sh             Проверки обёртки запуска
tests/test_tunnel.sh                 Проверки управления туннелем
tests/test_install_client.sh         Проверки установки клиентских команд
```

## Развёртывание на VPS

Требуются Linux с systemd, Git, Bash, Python 3.9+ по пути `/usr/bin/python3`
и права root через `sudo`. Сторонних Python-зависимостей нет.

Подключитесь к VPS по SSH. Клонируйте репозиторий, перейдите в каталог проекта
и запустите установщик:

```bash
git clone https://github.com/ivngrmk/proxy_server.git
cd proxy_server
sudo bash scripts/install.sh
```

Установщик проверяет Python и синтаксис исходника, копирует код в
`/opt/proxy-server`, устанавливает службу и сразу запускает её.
Служба включается в автозапуск и перезапускается через 5 секунд после завершения процесса.
Работа не зависит от открытого SSH-сеанса.

Служба использует отдельного пользователя, которого выделяет systemd
через `DynamicUser=yes`. Каталог данных `/var/lib/proxy-server` создаётся
systemd и сохраняется между перезапусками. Код принадлежит root и доступен
службе только для чтения.

## Настройки

При первой установке создаётся `/etc/proxy-server.env`.
Повторная установка сохраняет этот файл.

```bash
sudo nano /etc/proxy-server.env
sudo systemctl restart proxy-server
```

| Переменная | Значение в службе | Назначение |
| --- | --- | --- |
| `PROXY_BIND_HOST` | `127.0.0.1` | Адрес прослушивания |
| `PROXY_BIND_PORT` | `18181` | TCP-порт |
| `PROXY_DIR` | `/var/lib/proxy-server` | Каталог данных, содержащий `logs/` |
| `PROXY_HEARTBEAT_SECONDS` | `180` | Интервал записи о работе, секунды |
| `PROXY_MAX_LOG_BYTES` | `1048576` | Порог сокращения журнала, байты |
| `PROXY_KEEP_LOG_BYTES` | `262144` | Сколько последних байтов сохранять |

Используйте положительные значения интервалов и размеров, порт от 1 до 65535,
а `PROXY_KEEP_LOG_BYTES` задавайте меньше `PROXY_MAX_LOG_BYTES`.
Файл настроек использует синтаксис systemd: `KEY=value`, без `export` и
подстановок shell. Путь `PROXY_DIR` согласован с `StateDirectory` службы;
для смены каталога нужно также изменить unit и разрешения на запись.

По умолчанию прокси доступен только на VPS. В нём нет авторизации:
публикация порта в интернете даст другим пользователям доступ к прокси.
Для доступа с компьютера или кластера используйте SSH-туннель, описанный ниже.

## Настройка SSH-туннеля на клиенте

На компьютере или кластере, где запускается приложение, нужны Bash, OpenSSH,
curl и копия этого проекта. Если проект ещё не склонирован:

```bash
git clone https://github.com/ivngrmk/proxy_server.git
cd proxy_server
```

Установите клиентские команды для своего пользователя, без `sudo`:

```bash
bash scripts/install-client.sh
export PATH="$HOME/.local/bin:$PATH"
nano "${XDG_CONFIG_HOME:-$HOME/.config}/proxy-server/tunnel.env"
```

Теперь `with-proxy` и `proxy-tunnel` доступны из любого каталога. Если
`~/.local/bin` ещё не входит в `PATH`, добавьте строку `export PATH=...` выше
в `~/.bashrc`, чтобы команды были доступны в новых терминалах.
Исполняемые обёртки находятся в `~/.local/bin`, их код — в
`~/.local/lib/proxy-server`; перемещение или удаление клона не ломает команды.
Для обновления клиентского кода повторите `bash scripts/install-client.sh`.

При первой установке настройки копируются из `.env.tunnel` проекта, если
он уже существует, иначе создаются из примера `deploy/tunnel.env.example`.
Существующий файл `~/.config/proxy-server/tunnel.env` сохраняется.
При заданном `XDG_CONFIG_HOME` используется этот каталог вместо `~/.config`.

Укажите `VPS_HOST`, пользователя SSH и при необходимости путь `SSH_KEY` к
существующему приватному ключу. Пустой `SSH_KEY` использует обычные настройки
SSH и ssh-agent. Проверьте вход и ключ сервера обычным подключением
`ssh user@VPS_IP` (с `-i` и `-p`, если нужны). Ключ с парольной фразой заранее
загрузите в ssh-agent: фоновое подключение не запрашивает пароль.

Установленные команды читают отдельный файл настроек
`~/.config/proxy-server/tunnel.env` независимо от текущего каталога.
Это Bash-файл с поддержкой `$HOME`, в отличие от файла настроек службы
`/etc/proxy-server.env`. Пример сохраняет значения, уже экспортированные
в окружении. Для другого файла задайте `PROXY_CLIENT_ENV`.

Прямой запуск исходников через `bash scripts/with-proxy.sh ...` и
`bash scripts/tunnel.sh ...` также поддерживается. В этом режиме настройки
берутся из `.env.tunnel` в корне проекта; локальный файл исключён из Git.
Чтобы создать его, выполните `cp deploy/tunnel.env.example .env.tunnel`.

| Настройка | По умолчанию | Назначение |
| --- | --- | --- |
| `VPS_HOST` | требуется | Адрес VPS или имя из SSH config |
| `VPS_USER` | `root` | Пользователь SSH |
| `VPS_PORT` | `22` | Порт SSH |
| `SSH_KEY` | пусто | Необязательный путь к приватному ключу |
| `TUNNEL_HOST` | `127.0.0.1` | Локальный адрес туннеля |
| `TUNNEL_PORT` | `18181` | Локальный порт |
| `VPS_PROXY_BIND_HOST` | `127.0.0.1` | Адрес прокси со стороны VPS |
| `VPS_PROXY_BIND_PORT` | `18181` | Порт прокси на VPS |
| `TUNNEL_AUTO_START` | `auto` | Автозапуск из `with-proxy`: `auto`, `1` или `0` |
| `SSH_CONNECT_TIMEOUT` | `5` | Тайм-аут подключения SSH, секунды |

Управление туннелем:

```bash
proxy-tunnel start
proxy-tunnel status
proxy-tunnel stop
```

`start` открывает фоновое SSH-соединение и проверяет HTTPS через него;
в stdout выводится только URL прокси. Повторный `start` использует уже
работающее соединение. Если на локальном адресе уже отвечает исправный
прокси, например старый ручной туннель, он также используется, а скрипт
сообщает, что это внешнее соединение.

`status` проверяет реальный HTTPS-запрос и различает управляемый туннель
и внешний прокси. Код завершения — 0 при успешной проверке и 1 при
недоступности. Ошибки настроек и отсутствующих утилит имеют отдельный
ненулевой код.

`stop` через SSH control socket закрывает только туннель, созданный этим
скриптом с текущими настройками. Внешний прокси остаётся работать.
Перед сменой адресов или портов остановите управляемое соединение.
Control socket хранится в `~/.cache/proxy-server/tunnels`; для слишком
длинного домашнего пути задайте короткий `TUNNEL_STATE_DIR`.

Служба `proxy-server` на VPS должна быть установлена заранее. Клиентский
скрипт управляет SSH, а службой и Python-процессом управляет systemd.
Если проверка HTTPS после создания туннеля не проходит, новое соединение
закрывается и запуск завершается ошибкой. Туннель остаётся в фоне после
выхода из приложения; при обрыве автоматического переподключения нет.

## Запуск приложения через туннель

После настройки клиента запускайте команду через универсальную обёртку.
Она автоматически откроет туннель или использует уже работающий прокси:

```bash
with-proxy python -c 'import os; print(os.environ["HTTPS_PROXY"])'
```

Замените `python ...` командой нужного приложения и его аргументами.
Если оно установлено в Conda или другом окружении, сначала активируйте окружение.
Если обычная команда в терминале является функцией или алиасом, проверьте
её через `type -a COMMAND`. Для запуска конкретного исполняемого файла передайте
обёртке его полный путь. Команда `timeout N COMMAND` ищет исполняемый файл
в `PATH` и не вызывает одноимённую функцию текущей оболочки.
Обёртка требует Bash и curl, выполняет HTTPS-запрос через прокси и только после
успешной проверки запускает команду. Сообщения об этапах и ошибки выводятся
в stderr, stdout остаётся у приложения. Код завершения приложения сохраняется.
При `TUNNEL_AUTO_START=auto` туннель запускается, если задан `VPS_HOST`
и `PROXY_URL` указывает на локальный адрес туннеля. Без `VPS_HOST` сохраняется
режим проверки уже работающего прокси. `TUNNEL_AUTO_START=0` отключает
управление SSH; `1` принудительно включает его и требует совпадения
`PROXY_URL` с локальным адресом туннеля.

Передаются переменные `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY` и их варианты
в нижнем регистре. Приложение должно поддерживать эти переменные.
Исключения `NO_PROXY` и `no_proxy` по умолчанию содержат только локальные адреса;
для собственного списка задайте `PROXY_NO_PROXY`.
Экспорт действует на запускаемую команду и её дочерние процессы. Отдельный
запуск приложения из другого терминала или после выхода из обёртки этих настроек не получает.

Адрес прокси и адрес HTTPS-проверки можно изменить для одного запуска:

```bash
PROXY_URL=http://127.0.0.1:18181 \
PROXY_CHECK_URL=https://example.com/ \
with-proxy COMMAND ARG
```

Также поддерживаются `TUNNEL_HOST` и `TUNNEL_PORT`, если `PROXY_URL` не задан.
Тайм-ауты проверки: `PROXY_CONNECT_TIMEOUT=5` и `PROXY_CHECK_TIMEOUT=15` секунд.

## Диагностика туннеля

Открытый локальный порт ещё не подтверждает, что прокси на VPS доступен.
Проверьте всю цепочку с клиента:

```bash
curl -q -v --connect-timeout 5 --max-time 15 --noproxy '' \
  --proxy http://127.0.0.1:18181 https://example.com/ -o /dev/null
```

`200 Connection Established`, успешное TLS-соединение и `200 OK` подтверждают,
что HTTPS-запрос к проверяемому сайту прошёл через прокси. Доступ к конкретному
сервису, его авторизацию и запуск самого приложения проверяйте отдельно.
Для проверки другого сервиса замените HTTPS-адрес в команде.

Проверьте службу непосредственно на VPS:

```bash
ssh user@VPS_IP 'systemctl is-active proxy-server; ss -ltn sport = :18181'
```

Клиенту не нужно запускать Python-процесс через SSH: этим управляет служба
`proxy-server`. Ошибки SSH и проверки HTTPS не следует скрывать через
`|| true` или перенаправление stderr в `/dev/null`.

Для ручного запуска туннеля с ограничением ожидания и обнаружением обрыва:

```bash
ssh -n -f -N \
  -o BatchMode=yes -o ConnectTimeout=5 -o ConnectionAttempts=1 \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=15 -o ServerAliveCountMax=3 \
  -L 127.0.0.1:18181:127.0.0.1:18181 user@VPS_IP
```

Предварительно настройте вход по SSH-ключу и проверьте ключ сервера обычным
подключением `ssh user@VPS_IP`. Если порт уже занят существующим туннелем,
сначала выполните HTTPS-проверку, а не запускайте второй туннель на том же порту.
`ExitOnForwardFailure` проверяет создание перенаправления, но не доступность
конечного адреса на VPS; для этого нужна проверка HTTPS.

## Управление

```bash
sudo systemctl status proxy-server --no-pager
sudo systemctl restart proxy-server
sudo systemctl stop proxy-server
sudo systemctl start proxy-server
```

Ошибки процесса доступны в journald, подключения и сообщения о работе — в файле:

```bash
sudo journalctl -u proxy-server -n 50 --no-pager
sudo tail -f /var/lib/proxy-server/logs/proxy.log
```

## Обновление и удаление

В каталоге клонированного репозитория получите изменения и повторно запустите
нужный установщик. На клиенте:

```bash
git pull --ff-only
bash scripts/install-client.sh
```

На VPS:

```bash
git pull --ff-only
sudo bash scripts/install.sh
```

Код и unit обновятся, настройки и журналы сохранятся. Служба перезапустится;
текущие соединения при этом закроются. При ошибке запуска смотрите `status`
и `journalctl`; установщик завершится с ошибкой и не выполняет откат.

Удаление службы и установленного кода:

```bash
sudo bash scripts/uninstall.sh
```

Настройки `/etc/proxy-server.env` и каталог данных `/var/lib/proxy-server`
остаются на сервере. Удалите их вручную, если они больше не нужны.

## Локальный запуск и проверки

Из корня проекта:

```bash
python src/proxy_server.py
python -m unittest discover -s tests -v
bash tests/test_with_proxy.sh
bash tests/test_tunnel.sh
bash tests/test_install_client.sh
```

При прямом запуске настройки берутся из переменных окружения;
`/etc/proxy-server.env` автоматически не читается. По умолчанию журнал создаётся
в `src/logs/`. Пример локального запуска в PowerShell:

```powershell
$env:PROXY_BIND_PORT = "18181"
python src/proxy_server.py
```

Shell-проверки используют подставные SSH/curl и не обращаются к VPS или интернету.

Описание управления SSH: [ssh](https://man.openbsd.org/ssh.1),
[ssh_config](https://man.openbsd.org/ssh_config.5).
Описание параметров службы: [systemd.service](https://freedesktop.org/software/systemd/man/latest/systemd.service.html),
[systemd.exec](https://freedesktop.org/software/systemd/man/latest/systemd.exec.html).
